# DeepShieldAI

**Explainable Multimodal AI Framework for Deepfake Detection and Digital Content Authenticity Verification.**

DeepShieldAI is a full-stack application that classifies uploaded images, audio clips, video clips, news/text articles, and product/service reviews as genuine or fake (deepfake / AI-generated / synthetic). It also provides modality-specific explanations: Grad-CAM and LIME for images, waveform saliency for audio, 3-D Grad-CAM frame attribution for video, and SHAP or LIME token attributions for text and reviews.

---

## Architecture

- **Backend** — FastAPI (Python), PostgreSQL via SQLAlchemy + Alembic migrations, JWT auth with role-based access control.
- **Frontend** — React 18 + Vite, Tailwind CSS, with a dark/light theme toggle.
- **ML** — 6 independently trained detectors behind one `ModelRegistry`:

  | Modality | Model | Status |
  |---|---|---|
  | Image | MobileNetV2 (Keras 3, PyTorch backend) | Live |
  | Audio | wav2vec2-base (fine-tuned) | Live — best-performing model (F1 0.98) |
  | Video | R3D-18 (fine-tuned) | Live, but see known limitations below |
  | Text / News | DistilBERT (fine-tuned) | Live |
  | Review | DistilBERT (fine-tuned) | Live |
  | Bot / Account | XGBoost on account metadata | Live — second-best model (F1 0.926) |

  See [`docs/MODELS.md`](docs/MODELS.md) for full per-model architecture, training data, metrics, and known limitations of each model — read this before quoting any accuracy number in a report.

- **Explainability** — Grad-CAM and LIME for Image, SHAP and LIME for Text/Review/Account, waveform saliency for Audio, and 3-D Grad-CAM frame attribution for Video (`backend/xai/`). Audio returns time-window importance and Video returns sampled-frame importance; neither is presented as a fabricated image heatmap.
- **Async inference pipeline** — Analysis requests are queued to a Celery worker (Redis as broker) rather than running inline in the API request, so a slow Audio/Video analysis never blocks every other request. See [`docs/ASYNC_PIPELINE.md`](docs/ASYNC_PIPELINE.md) for the full design.
- **Retrieval** — ChromaDB stores embeddings generated by `all-MiniLM-L6-v2`. The RAG page supports document ingestion and semantic passage retrieval; it currently returns retrieved passages rather than generating an LLM-written answer. Knowledge sources can be uploaded through the UI and indexed with a chunk size from 100 to 5000 (500 is recommended).
  On Windows, the embedding step (`sentence-transformers` → scikit-learn) can fail to import if a security policy — Smart App Control, or an IT-managed Application Control/WDAC policy on a corporate laptop — blocks one of scikit-learn's compiled extensions. The API detects this at first use, not at startup: RAG endpoints return `503` with an explanation instead of taking down the rest of the app, and every other feature (auth, uploads, all 6 detectors) is unaffected.
- **Not yet built** — LIME explainability for Audio/Video, automatic folder synchronization for `knowledge-sources/`, full-coverage automated tests (a starter suite covering auth/documents/predictions exists — see "Running tests" below), and CI/image-publishing automation.

## Run everything with Docker

The fastest way to see the whole stack running — Postgres, Redis, the API, the Celery worker, and the built frontend — is one command:

```bash
cp backend/.env.example backend/.env   # if you don't already have one; set a real SECRET_KEY
docker compose up --build
```

Then open `http://localhost:5173`. See [`docs/DOCKER.md`](docs/DOCKER.md) for the full architecture, design decisions, and first-run seeding steps. The rest of this README covers running each piece directly on your own machine instead, which is still the faster loop for active development.

## Backend setup

```bash
cd backend

# 1. Create and activate a virtual environment
python -m venv .venv
.venv\Scripts\activate        # Windows
# source .venv/bin/activate   # macOS/Linux

# 2. Install dependencies
pip install -r requirements/ml.txt     # full app: API + all 6 ML detectors + explainability + RAG
# pip install -r requirements/base.txt # API only (auth, CRUD, dashboard) — no ML endpoints
# pip install -r requirements/dev.txt  # base.txt + pytest/ruff/black/mypy tooling

# 3. Configure environment
copy .env.example .env        # Windows
# cp .env.example .env        # macOS/Linux
# then edit .env: set a real SECRET_KEY (see the comment in the file) and
# a DATABASE_URL that points at a database you've already created, e.g.:
#   createdb deepshieldai

# 4. Run migrations
python -m alembic upgrade head

# 5. Seed reference data (roles, document types) and create your first admin user
python -m scripts.seed_all
python -m scripts.create_admin

# 6. Run the API
uvicorn app.main:app --reload --port 8000
```

The API is now at `http://localhost:8000`. Interactive docs (Swagger UI) are at `http://localhost:8000/docs` — only available while `DEBUG=true` in `.env`. To check which of the 6 detectors actually loaded (i.e. their weight files were found and are valid), hit `GET /api/predictions/models` once logged in.

> Run `python -m scripts.xxx`, not `python scripts/xxx.py` — the `-m` form is required so the script can import the `app` package. Running the `.py` file directly fails with `ModuleNotFoundError: No module named 'app'`.

### Model weights

Trained model weights are **not stored in git** (they total roughly 800 MB+ and GitHub rejects anything over 100 MB per file). You'll need to get them separately from whoever shared this project with you, and place them so the layout matches:

```
backend/models/
├── image/  best_model.keras
├── audio/  config.json, model.safetensors, preprocessor_config.json
├── video/  video_model_finetuned.pth, class_names.pkl
├── text/   config.json, model.safetensors, tokenizer files
├── review/ config.json, model.safetensors, tokenizer files
└── bot/    bot_xgb_model.json, feature_schema.json
```

The app still starts without them — any detector whose weights are missing just reports itself unavailable (`/api/predictions/models`) instead of crashing the whole API.

## Frontend setup

```bash
cd frontend
npm install
npm run dev          # starts the Vite dev server, default http://localhost:5173
```

Other scripts: `npm run build` (production build to `frontend/dist/`), `npm run preview` (serve that build locally), `npm run lint`.

The frontend talks to `/api` (and `/docs`) as relative paths — the Vite dev server proxies them to the backend, per `API_TARGET` in `frontend/vite.config.js` (defaults to `http://localhost:8000`). If you run the backend on a different port, update `API_TARGET` there. For a production build (`npm run build`), there's no dev-server proxy, so make sure the backend's `.env` `CORS_ORIGINS` includes wherever the built frontend is served from.

## Typical local run

Two terminals:

```bash
# terminal 1
cd backend && .venv\Scripts\activate && uvicorn app.main:app --reload --port 8000

# terminal 2
cd frontend && npm run dev
```

Then open `http://localhost:5173`, register an account (or log in with the admin user from `scripts/create_admin.py`), and upload a file to try detection.

### RAG knowledge base

The project stores general detection guidance in `knowledge-sources/`. These files are not indexed automatically. To use them, upload each source as a Text document, open the RAG page, select the document, and click **Index a document**. Use `all-MiniLM-L6-v2` and a chunk size of `500`. After indexing, questions return the nearest passages with source filenames and page metadata.

The vector store is persisted at `backend/storage/chroma/` and is ignored by git because it is generated runtime data. Re-index sources after changing their content.

## Running tests

```bash
cd backend
pip install -r requirements/dev.txt   # if you haven't already (base.txt + pytest/ruff/black/mypy)
pytest
```

The suite (`backend/tests/`) runs against an in-memory SQLite database via a `get_db` dependency override — never against your real Postgres database — and fakes the ML registry rather than depending on trained model weights being present, so it's fast (a few seconds) and safe to run on a fresh checkout with no weights, no Redis, and no Celery worker running. It covers auth (registration always defaults to the "User" role, login, token validation), document upload (including the `.json` Text-vs-Account ambiguity `document_type_name` exists to resolve — see `docs/MODELS.md`/this file's ML section), the prediction pipeline's `start_analysis`/`run_analysis` split (Phase 11 — a dispatched task, a crashed detector, an unsupported modality, a since-deleted row), and `bot_preprocessing.extract_features()`'s handling of malformed input. It is a starting point, not full coverage — the explainability (`xai/`) and RAG (`rag/`) modules aren't exercised yet, since both need their heavy dependencies (torch, shap, chromadb) actually installed to test meaningfully rather than mocked.
